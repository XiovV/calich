# A Calendar's external state moves to a Source table; a Connection is one grant to many Calendars

Status: accepted — amends ADR-0032

ADR-0032 made a Subscribed Calendar "a Calendar with a source URL": fourteen nullable columns bolted onto `calendars`, with `source_url IS NOT NULL` as the de facto test for "this Calendar is externally owned and not writable here". That shape does not survive a second kind of external source. This ADR extracts the external state into a **`calendar_sources`** table with a kind discriminator, and introduces **`connections`** for the OAuth grant.

## Why the shape has to change

A Subscription is **one Calendar to one URL**. A Connection is **one OAuth grant to many Calendars** — a single authorization yields the primary calendar, every secondary calendar, every calendar shared *to* that account, and Google's auto-generated Holidays and Birthdays. There is no way to express a 1:N grant as more columns on `calendars` without duplicating the tokens onto every row, which then have to be refreshed and revoked in lockstep. The cardinality difference forces a new entity above Calendar whatever else we do.

Given that, leaving Subscription's fourteen columns where they are would take `calendars` past thirty columns, most NULL on most rows, and would leave *two* answers to "is this Calendar externally owned?" that every guard, the poller, the reconciler and the CalDAV privilege logic must keep in sync forever. The first time those two answers disagree is a User editing an Event that the next Refresh obliterates — ADR-0032's named failure mode, arrived at by a different route.

**The timing is the argument.** ADR-0048 squashes migrations until the first release, and there is exactly one migration file. Restructuring `calendars` costs an edit today and a real migration with a real backfill the day after the first tag. This is the cheapest this decision will ever be, and it does not get cheaper by waiting.

## Decisions that follow from it

- **`Source` is the umbrella and the single guard.** A Calendar has zero or one Source; a Subscription is one kind, a Connection-derived link is the other. Every read-only check keys off "has a Source", replacing ADR-0032's `source_url IS NOT NULL`. The `EventService` guard ADR-0032 established is unchanged in structure — it just asks a better question.
- **Read-only is a property of the Source's *mode*, not of the Source existing.** Today every Source is read-only, so this distinction buys nothing yet. It is drawn now because write-back is a stated intention, and the alternative is that "external" and "read-only" fuse into one concept across the guards, the CalDAV privilege set and the UI — after which separating them is a refactor rather than a flag. For the same reason the Provider's own event id **and a per-series etag** are stored from the outset: they are what makes a series addressable back at the Provider, they are free to capture while writing the mapper, and they are unreconstructable later without a full resync.
- **A Connection belongs to a User; its Linked Calendars belong to Workspaces.** One OAuth grant per (User, Provider account) regardless of how many Workspaces the User is in — one token, one consent, one refresh cycle. Selecting calendars places them in the Workspace active at the time, and the picker is re-runnable elsewhere, so work calendars can live in one Workspace and personal ones in another. One Google calendar may therefore appear in two Workspaces as two Calendar rows, fetched twice. That waste is accepted rather than designed away: deduplicating fetches means sync state keyed on (Connection, provider calendar) fanning out to N Calendars, which is a third level of indirection to save one HTTP request per cycle at self-hosted scale.
- **Refresh tokens are encrypted at rest with a key from the environment, never stored in `DATA_DIR`.** This departs from ADR-0032, which stores a Subscription's HTTP Basic password in plaintext on the reasoning that a replayable credential cannot be hashed and there is no keychain to defer to. Both halves of that reasoning still hold — encryption is not hashing, and the key has to live somewhere. What changed is the blast radius and the exposure path. A feed password unlocks one feed; a Google refresh token is a standing grant against an entire account. And the deployment story *instructs* self-hosters to mount and back up `DATA_DIR`, which makes a backup tarball in the wrong place the realistic exposure rather than an attacker with shell access. Keeping the key outside that directory means the routine accident stops being a compromise. Losing the key costs re-authorization, not data — which is what makes this trade cheap.
- **The Owner is the connecting User, and a Linked Calendar Shares like any other Calendar.** Access resolves normally and is then clamped read-only. A Google calendar merely shared *to* the connecting User can therefore be re-shared onward inside a Workspace, to people its original Google owner has never heard of. Gating that on Google's `accessRole` was considered and rejected: it makes Access depend on a third party's ACL that changes without notice, and it stops only the honest path — the connecting User can already see every Event and could export them by hand.
- **Attendees are not mirrored onto Linked Calendars.** Google's attendees are arbitrary email addresses, while `attendees.user_id` is `NOT NULL REFERENCES users(id)` and ADR-0046 requires the target to be a Workspace member — the model cannot represent `alice@partner.com` at all. Widening Attendee to be email-first (with `user_id` resolved only when it matches, and only a resolved `user_id` conferring the visibility grant) was the considered alternative, and is the shape iCalendar's own `ATTENDEE` has. It was declined to keep ADR-0046 shipping unchanged. **The cost is recorded deliberately: this returns with write-back or with Outlook, and by then ADR-0046 will have shipped, so widening will cost a migration instead of an edit.**
- **What a Linked Calendar does carry, beyond title/start/end/all-day/`tzid`/`RRULE`/description/location:** the connecting User's own RSVP status (from the `self` attendee's `responseStatus`, rendered as a read-only badge — a declined meeting still occupying the grid is actively misleading, and this needs no Attendee row), the conference join URL (its own nullable field, mapping to iCalendar `CONFERENCE`, rather than smuggled into `location`), and Google's `colorId` converted to hex, which drops straight into the existing Event color of ADR-0043.
- **Drive attachments are not carried.** ADR-0040 states that an Attachment is bytes this instance stores and that a link to a file elsewhere is explicitly not modelled. That still reads correctly here, and carrying Google's file links would mean either a new link concept or amending ADR-0040 — neither earned by this feature.
- **A Source's alarms stay opt-in and off by default,** reusing ADR-0032's `keep_alarms` verbatim on the Source rather than adding a per-kind rule. The reasoning is stronger here than for feeds: anyone connecting Google definitionally has a Google account already notifying them on every device, so double-firing is not a risk but the default outcome. The toggle exists for the User who has deliberately made this app their primary surface and silenced Google.
- **Disconnect demands an explicit disposition,** defaulting to keeping the Linked Calendars as ordinary owned Calendars with the Source dropped and Provider ids cleared, the alternative being outright deletion. This follows ADR-0037, which already requires an explicit disposition for the Calendars a deleted account owned. Deletion is unrecoverable, the mirror may be the User's last copy if they are leaving Google, and — since Linked Calendars are Shareable — it would strip a Calendar out of other Members' sidebars and tombstone every series to their phones. The confirmation must say so when Shares exist.
- **Failure never deletes anything.** A revoked or expired token, or a calendar vanishing from the Provider's list because someone unshared it, is a *needs-attention* error in ADR-0033's existing two-class model: last good state preserved, Connection never auto-disabled, Events frozen and flagged. Only the User deletes a User's data.

## Consequences

- **Working Subscription code gets touched for a feature that is not about Subscriptions.** This is the real cost and it is paid up front. It is bounded by the migration squash — the fourteen columns move once, in one edit, with no backfill against any database that exists.
- **`calendar_sources` is where the next Source kind lands.** A generic CalDAV client (iCloud, Nextcloud, Fastmail) is the obvious third kind and needs no new structure, which is a large part of why the extraction is worth doing now rather than when Outlook forces it.
- **A nullable `user_id` on a widened Attendee is a landmine we chose not to plant yet.** Recording it here so that whoever widens it later reads this first: an unresolved Attendee must never confer visibility, and every authorization path has to be re-checked against that, not just the invite path.
