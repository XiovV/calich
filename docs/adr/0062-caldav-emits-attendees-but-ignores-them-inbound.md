# CalDAV emits `ATTENDEE`, and ignores it on the way back in

Status: accepted — a named ADR-0026 lossy case; extends ADR-0025 and ADR-0059

The codec emits no `ATTENDEE` and no `ORGANIZER` at all today, so a native client syncing an Event with fourteen guests sees a meeting with nobody on it. That is an unrecorded lossy round-trip — ADR-0026's whole posture is that lossy round-trips are *deliberate, named exceptions*, and dropping the entire guest list was never named. ADR-0059 makes it worse by forcing `ORGANIZER` into the codec: an event carrying `ORGANIZER` and no `ATTENDEE` reads to most clients as a published event rather than a meeting.

## Emitted on every target

`ATTENDEE;CN=<Name>;PARTSTAT=<response>:mailto:<address>` — the User's Email for a Member row, the stored address for an email-shaped one (ADR-0058) — over CalDAV, in Calendar files, and in the Invitation. Guests and their responses become visible in Apple Calendar, Thunderbird, and any export.

The mapping is nearly free: `attendees.response` already stores iCalendar's `PARTSTAT` vocabulary verbatim (ADR-0046 chose the full set for exactly this reason), so this is a rename at the boundary rather than a translation.

## Ignored on inbound `PUT`

A native client may now `PUT` an Event back with `ATTENDEE` lines added or removed. Those changes are discarded, and the guest list is re-emitted from this app's own state on the next `GET`.

Honouring them would mean a Thunderbird sync can cause this instance to send Invitations, in the self-hoster's name, to addresses nobody typed here — ADR-0059's outbound mail triggered by a third-party client's idea of a diff. The guest list is owned by this app's API; CalDAV reads it.

This is the same shape of decision as ADR-0027's alarm double-fire resolution: a capability a synced client appears to offer, deliberately not wired up, recorded so nobody later reads its absence as an oversight.

## Consequences

- **A new entry in ADR-0026's ledger of deliberate losses**: attendee edits made in a native client are discarded silently, and the next sync restores the server's list.
- **Letting native clients manage guests remains open** and is a substantially larger feature — inbound iTIP generated by a third party, with its own authorization and abuse questions — not an extension of this one.
- **`PARTSTAT` is now visible to Members over CalDAV**, so an Attendee's Response is readable by any client syncing a Calendar they have Access to, not only through the web UI.
