# httpOnly refresh-token cookie now that a backend exists

Status: supersedes ADR-0008; amended by the `COOKIE_SECURE` note below (#239), whose default is itself reversed by the second amendment (#257)

The refresh token is now issued and validated by the Go backend as an `httpOnly`, `Secure` cookie, not stored in `localStorage`. The access token is kept in memory only (not persisted client-side); a page refresh re-authenticates silently against the refresh cookie via `refreshAccessToken`. ADR-0008 explicitly named this cookie pattern as the intended long-term design, blocked only on a backend existing to issue it — that backend now exists. `httpOnly` cookies aren't readable by JS, closing the XSS-based token theft risk that came with `localStorage`, which matters more here since this app is meant to run in self-hosted environments with varying levels of hardening.

## Amendment: `Secure` is operator-configurable (#239)

`Secure` was originally hardcoded `true`. In practice, a browser silently discards a `Secure` cookie sent over plain HTTP from an origin it doesn't trust — so on a plain-HTTP deployment (the first thing most self-hosters try, e.g. `http://192.168.1.50:8080`) the Refresh token cookie was never stored at all. Login appeared to succeed, then the User was bounced back to the login screen on the next page load or once the 15-minute access token expired, with no error surfaced. This is invisible in local development, where `http://localhost` is treated as a trustworthy origin.

`Secure` is now controlled by `COOKIE_SECURE` (`config.Config`), defaulting to `true` — an operator who sets nothing keeps this ADR's original behaviour. Deriving it instead from `X-Forwarded-Proto` or `r.TLS` was considered and rejected: it depends on reverse-proxy configuration the operator may not control, and fails silently in exactly the same way when the header is absent. `HttpOnly` and `SameSite=Lax` are unaffected — only `Secure` is configurable, and `setRefreshCookie`/`clearRefreshCookie` always agree on the same setting so a cookie set under one value is still clearable under that value. The default stays `true` because the risk this ADR closes (XSS-based token theft against a `Secure`, `httpOnly` cookie) is worse than the plain-HTTP failure mode this amendment fixes; turning it off is an explicit, documented (see README) opt-in for a deployment that has already decided not to run TLS.

## Second amendment: the default flips to `false`, and the mismatch is reported (#257)

`COOKIE_SECURE` now defaults to **`false`**, reversing the first amendment's choice. That choice optimized for the instance that already has TLS; this one optimizes for the path a self-hoster actually walks. A LAN-only deployment is a legitimate end state, and a LAN deployment that later grows a reverse proxy is the common one — so the plain-HTTP case is not a rare misconfiguration to be defended against, it is step one for nearly everyone. Defaulting to `true` meant that step one presented as a broken login with nothing in the logs, which is a bad first contact with the software.

What made the original default defensible was the asymmetry in how each wrong value fails: a wrong `true` fails loudly and self-corrects, whereas a wrong `false` works perfectly and is never noticed. Flipping the default without addressing that asymmetry would trade a visible problem for an invisible one. So the flip is paired with the reporting that removes it — `setRefreshCookie` now warns, once per process, when it issues a non-`Secure` cookie on a request that arrived over TLS (`r.TLS`, or `X-Forwarded-Proto: https` from a terminating proxy). The operator who graduates to a reverse proxy gets told, at the moment they graduate, that the setting is now wrong for them.

This does not reopen what the first amendment rejected. That rejection was of *deriving* `Secure` from those signals, and it was right: an absent `X-Forwarded-Proto` would silently downgrade the cookie, which is the failure this ADR exists to prevent. Reporting inverts the cost of being wrong. A false negative in the derivation loses the token; a false negative in the warning loses a log line. Same signal, opposite blast radius, so the same evidence supports warning on it while refusing to act on it.

The residual risk is unchanged and still real: without `Secure`, the Refresh token rides along on any plaintext request to the same host — including one an attacker induces with an `<img src="http://…">` on an unrelated page — and is readable on-path before any HTTPS redirect can intervene. HSTS mitigates this only after a prior visit or a preload entry. Every deployment reachable from outside a trusted LAN should set `COOKIE_SECURE=true`, and the README's reverse-proxy instructions say so at the point where the operator is configuring exactly that.
